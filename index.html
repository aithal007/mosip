Inji Conformance Gate

The OpenID conformance suite is built for a human clicking through a wallet UI — workable once for a certification submission, unusable on every PR. This turns it into an unattended, click-free, benchmark-gated release gate for Inji Certify and Inji Verify, with results surfaced inside MOSIP's own api-testrig reports.

How it works

1
One command starts everything. ./run-conformance.sh --component certify|verify | --combined --parallel boots the pinned OpenID suite, a TLS gateway, Inji Certify and Inji Verify via docker-compose, seeds the SD-JWT credential configuration, and runs the plans.
2
The unmodified upstream runner drives the suite. run-test-plan.py from the OpenID Foundation runs as a subprocess — plan creation, retries, signed exports are all upstream. Upgrading the suite is one line.
3
A handoff agent keeps the run alive. The suite pauses whenever a real issuer or verifier must act. The agent polls the suite's own state and answers each pause using Inji's real APIs — credential offers from /pre-authorized-data, authorization requests from /v2/vp-request — exactly what a real wallet or verifier UI would do.
4
REVIEW results are resolved with evidence, not a human. Where the suite would show a placeholder and ask a person to eyeball a screenshot, the resolver asks Inji Verify for its own verdict, cross-checks it against what the module expected, and uploads a PNG evidence card into the suite for the audit trail.
5
An issue-linked benchmark gates releases. Every expected failure (Inji is pre-1.0) carries a tracked GitHub issue. The gate fails only on regressions; anything that starts passing is flagged STALE_BENCHMARK so the benchmark never rots. Shims are declared in the plan manifest and printed in every report — nothing is hidden.

Keep upstream unmodified

Plan execution, parallel queues, retries and signed exports come from the upstream runner. The harness adds only what upstream lacks: handoff to an external system under test.

Real APIs, not mocks

Every handoff call is made to the real Inji endpoints, rebuilt exactly as Inji Verify's SDK does — so the suite tests what a production wallet would see.

Fail closed

Missing plans, zero selected modules, modules stuck in WAITING, or unknown verdicts in the Java bridge → exit 1/2. A blind spot can never report success.

Pin + disclose

Suite tag, Inji images and upstream refs are pinned in versions.env. Every compatibility shim is declared in the plan manifest and printed in reports, next to its tracking issue.

The REVIEW problem, solved

The OID4VP plan produces 7 REVIEW placeholders that a human would resolve by examining screenshots. The harness resolved all 7 automatically: it compared Inji Verify's own verdict with the outcome each module expected, attached PNG evidence cards to the suite, and — against MOSIP's own manual run (inji-verify#2013) — resolved 6 of those that had been left for a person.

Every verdict is explicit

VerdictMeaning
PASSmodule passed the suite
KNOWN_ISSUEfailed, but matches an issue-linked benchmark entry — tracked, visible, not a regression
FAILnew failure or benchmark-item regression → gate fails (exit 1)
STALE_BENCHMARKan expected failure now passes → benchmark entry should be removed
SKIP / INCOMPLETEmodule not runnable / never finished → fails the gate; never silently ignored

Beyond the suite: adversarial probes

The suite only checks what the spec's happy paths cover. icg probe attacks Inji with what the suite doesn't cover — and asserts the system refuses:

  • credential offers for unknown configurations, replayed pre-authorized codes, wrong tx_code, path-inserted metadata (inji-certify#967)
  • an SD-JWT tamper corpus — 15 mutated SD-JWT VC presentations (altered/duplicated disclosures, wrong key-binding JWT, wrong nonce, audience, sd_hash, alg=none, embedded jwk, expired credentials, claim collision…) each tied to its RFC or CVE
  • a strict reference verifier and a mutation-test self-check: each of its 12 rules is switched off in turn and the probes must notice — currently 12/12 caught. An untampered control must pass first, or the run reports inconclusive instead of a false pass

Probe results are JSON, never feed the OpenID gate, and degrade to SKIP when a request cannot be made.

Certification readiness, honestly stated

icg readiness reports, one row per capability gap, what still blocks each HAIP profile plan (the ones OpenID self-certification counts): Verify needs direct_post.jwt, x509_hash signed requests and mdoc; Certify needs enforced DPoP, client attestation, the authorization-code flow with PAR, and the path-inserted metadata URL. This is a pre-certification harness — no OpenID certification is claimed anywhere.

Run it yourself

# Prereqs: Docker Desktop (≥10 GB), Python 3.10+, git, bash
git clone https://github.com/aithal007/mosip.git && cd mosip
./run-conformance.sh --component certify       # OID4VCI issuer plan → Inji Certify
./run-conformance.sh --component verify        # OID4VP verifier plan → Inji Verify
./run-conformance.sh --combined --parallel     # both, one consolidated report + gate

# open the report
open results/<run-id>/conformance-report.html

# adversarial probes against a running stack
python -m icg probe --component certify
python -m icg readiness     # what blocks HAIP self-certification
python -m icg selftest      # probe mutation self-test, no Docker needed

Exit codes: 0 gate passed · 1 regression · 2 infrastructure error. localhost.emobix.co.uk resolves to 127.0.0.1 via public DNS — no hosts-file edits.
